# 工程协作与编码原则

## 1. 文档定位

本文定义 MechStorm 项目中通用的架构分析、编码、沟通和执行原则，适用于参与项目的开发者与 AI 编码助手。

本文只规定跨模块通用的工程协作方式，不重复具体框架 API、战斗架构和当前任务要求。发生冲突时按以下优先级执行：

1. 安全要求和用户当前明确指令。
2. `CLAUDE.md` 及项目技术规范。
3. `DEVELOPMENT_PROGRESS.md` 当前任务、验收标准和决策记录。
4. `BATTLE_ARCHITECTURE_ROADMAP.md` 等领域架构文档。
5. 本文的通用工程原则。

## 2. 核心结论

所有工作遵循以下总原则：

- 架构分析从问题本质和约束出发，不从现成模式或框架名称出发。
- 实现优先选择满足当前验收标准的最简单方案。
- 修改范围紧贴需求，不主动扩大任务边界。
- 输出先给结论，再给依据、方案、风险和验证结果。
- 多步任务以可验证目标驱动，持续执行到验收通过或明确受阻。

## 3. 架构与设计原则

### 3.1 第一性原理

分析架构、模块或代码组合时，先回答：

1. 要解决的真实问题是什么。
2. 当前必须满足哪些业务和技术约束。
3. 哪些状态、行为和依赖是不可省略的。
4. 哪些复杂度来自当前需求，哪些只是对未来的猜测。
5. 最小可验证方案是什么。

不得仅因为某个模式、框架或参考项目流行，就默认引入。外部方案只能作为证据和备选，最终设计必须映射到 MechStorm 的项目语言、当前阶段和验收标准。

### 3.2 DRY、KISS、SOLID 与 YAGNI

- **DRY**：消除已经出现且语义一致的重复，不为可能出现的重复提前抽象。
- **KISS**：优先使用直接、可读、可测试的实现，避免无必要的层级和间接调用。
- **SOLID**：按职责和变化原因拆分模块，依赖稳定契约，不机械追求接口数量。
- **YAGNI**：需求未要求、当前验收不依赖、近期没有明确使用方的能力不实现。

原则冲突时，优先保证正确性和可理解性，其次保证当前可维护性，最后才考虑未来扩展性。

### 3.3 规模约束

- 单个函数原则上不超过 50 行。超过时先判断是否混合了多个职责，再按语义拆分。
- 单个类或代码文件超过 500 行时，必须识别其职责、依赖和变化原因，评估是否需要拆分。
- 不能只为满足行数机械拆文件。拆分后的对象必须拥有清楚职责和稳定边界。
- 一次性流程不建立通用抽象；只有出现真实复用或独立变化原因时才提取。

## 4. 编码规范

### 4.1 遵循现有代码

- 编码前先读取相关目录、相邻实现、测试和项目规范。
- 复用项目已有库、模式和命名，不擅自引入新依赖。
- 与周边代码保持一致，除非现有写法违反项目硬约束或会直接导致缺陷。
- 使用有意义的类型、变量和函数名称，让命名承担主要说明职责。

### 4.2 注释与错误处理

- 只为复杂意图、关键约束和反直觉行为添加注释。
- 不添加重复代码字面含义的注释。
- 外部输入必须校验，不能假设其天然可信。
- 错误必须显式返回、抛出或记录，不允许静默吞掉。
- 密钥、密码、API Key 等敏感信息必须来自环境变量或安全配置，不得硬编码或写入日志。

### 4.3 精准修改

- 每一行差异都必须对应当前需求、必要修复或本次改动产生的清理。
- 不顺手格式化、重命名或重构无关代码。
- 发现无关死代码时只报告，不擅自删除。
- 本次改动产生的无用导入、变量、函数和临时文件必须清理。
- 未经明确要求，不删除、覆盖或移动用户未跟踪文件。

### 4.4 避免过度防御

防御应对应真实边界和可发生的失败，不以“多检查更安全”为由增加分支、状态或包装。编写、重构和审查代码时遵循：

- **边界校验，内部信任契约**：校验外部输入、配置、资源加载结果和可变化的生命周期；构造、初始化或阶段进入已经保证的依赖，不在每层调用重复判空/检查就绪。异步等待后可能失效的条件不能当作永久不变量。
- **框架契约优先，业务不重复兜底**：先核对框架/底层API已有的异常、空值、销毁和加载处理。框架已保证结果或已负责暴露错误时，业务直接使用其契约，不再补同义判空、异常包装、默认值或恢复路径；框架已覆盖大部分预期外情况时，不为理论上剩余的可能性机械增加防御。只有当前业务存在明确、实际可达且未被底层覆盖的风险时才补充处理，并明确其责任边界；不能因此假定框架覆盖所有失败。
- **按所有权判断生命周期风险**：对象由当前流程独占管理、没有正常外部关闭/替换路径时，不为“其他代码也许会随意销毁它”增加轮询、分支或取消机制。流程退出使用已有生命周期取消；以后新增关闭入口时，同步设计取消/返回语义，而不是提前假设所有权随时会被违反。
- **初始化顺序就是内部契约**：调用方已经等待初始化完成，且后续调用间没有新的失效边界时，直接使用初始化结果，不再维护“已就绪”标记或重复检查销毁状态。标记只用于有实际消费方、不能从现有执行顺序确定的独立事实。
- **释放由所有者统一编排**：所有者已负责先停止任务、解绑调用方再销毁对象时，不再通过被拥有对象的关闭事件建立第二条释放链，也不让普通调用用“已销毁则返回”掩盖违反调用顺序的错误。释放入口的幂等判断和部分初始化清理仍保留。
- **不要静默掩盖编程错误**：必需依赖缺失、非法状态等内部错误应暴露，不能通过 `?.`、默认值、空集合或提前返回伪装为正常成功；合法的可选值、玩法拒绝和资源加载失败仍按各自契约处理。
- **异常只在能负责处理的边界捕获**：需要恢复、释放资源或记录诊断的异步任务入口可以捕获异常；不要在每层调用都增加宽泛 `catch`。无法处理时让异常传播，需要重新抛出时保留原始堆栈。
- **清理不等于恢复**：正常取消按生命周期结束处理；开发错误应直接暴露，必要清理后用 `throw;` 传播原异常，不能仅记录日志后吞掉。失败后返回入口、重试或重新同步必须有明确的业务决定，不能凭猜测增加。明确要求“本次操作异常即退出并返回入口”时，可以在所属流程边界统一执行，但这只代表放弃失败操作，不代表修复了异常或可以继续使用失败状态。检查后抛出具体契约错误不属于兜底，重点审查后续是否将错误吞掉或伪装成正常流程。
- **取消机制匹配实际并发**：串行流程默认复用所属生命周期的 token；对象由同一流程独占管理且始终先取消再销毁时，不额外创建对象销毁 token、子 CTS 或 linked CTS。只有存在独立中断、并行分支或旧任务覆盖新任务的真实需求时，才增加对应机制。不为假设中的抢占建立多层保护。
- **不重复已完成的状态切换或取消检查**：初始化或阶段退出已设置的状态，后续步骤不再重复设置来“确保一次”；框架自动变更由已有的统一策略处理。已核对某个 await 会检查同一 token 并以取消结束，恢复后又没有新的失效边界时，不紧接着重复检查取消；不支持取消的加载和迟到结果隔离仍按实际契约处理。
- **状态按实际语义表达**：不为减少 bool 而保存没有消费方的 Exception 或增加包装对象；互斥玩法阶段用明确状态表达，资源请求记录、失败标记等独立事实仍可使用 bool。
- **释放兜底与业务重复检查分开看**：取消、部分初始化失败、迟到加载和重复释放是实际生命周期边界，应保留必要的幂等清理；不要因精简而删除安全校验、事务校验、同帧输入限制或真实的旧任务隔离。
- **幂等清理直接调用**：框架保证幂等的关闭、释放接口（如 TE 的 `CloseUI` 对不在栈中的窗口为空操作）直接调用，不为“是否调用过”单独记录标记。只有框架不保证幂等，或释放动作本身有副作用需要判断时，才保存状态。
- **等待外部结果必须有明确出口**：框架等待超时后若返回未完成对象（如 TE `ShowUIAsyncAwait` 超时后返回未加载完成的窗口），业务不能直接进入依赖完成状态的等待，应在返回后检查并抛出具体错误。超时时长由框架决定时，需在任务记录中说明该取舍。
- **明确且易改的失败直接暴露**：某种错误一旦发生就会以异常或空引用直接暴露，且修复成本低、影响范围清楚时，不为推测中的触发路径增加守卫、存活标记或恢复分支。只有出现真实的触发路径，或暴露后的代价不可接受时，才在对应边界补充处理。

新增防御前，应能说明它防止的具体失败、为何上游契约尚未覆盖，以及失败后由谁处理。无需为每处检查增加说明性注释，也不对现有代码机械删检查或批量套用防御模板。

### 4.5 异常捕获时机

- **当前战斗开发策略（2026-10-26）**：ProcedureBattle 的程序错误直接暴露，由开发者修复，不自动清理或返回主界面；不因异步入口独立就增加失败捕获。下述允许捕获的场景不构成必须捕获的要求，只有另行明确相应处理需求才采用。正常撤退、重开与离场取消不属于异常恢复。
- **默认不写 try/catch，程序错误直接暴露**。由开发者定位并修复错误，不为“更安全”或“防止报错”自动增加兜底。异常应传播到能负责处理它的边界；异步方法、独立任务入口、事件回调或拥有资源本身，都不意味着必须捕获。
- **先有处理职责，再决定捕获位置**。写 try 前说明捕获后具体承担哪项必要清理、已定义的恢复或有效诊断，以及为什么现有框架/所有者未覆盖。仅说“这是异步入口”或“这里有资源”不构成理由。独立任务的调用关系只决定上层能否观察异常，不会自动产生失败处理需求。
- **不擅自增加失败策略**。自动清理整场、返回入口、重试、弹窗或允许继续运行，都必须有明确需求，不能由一个宽泛 catch 顺带决定。正常取消、正常离场释放和异常恢复分别判断；直接暴露错误不等于删除必要的资源安全，局部资源仍按 `using` / `finally` 或明确的所有者释放契约处理。
- **允许捕获的情况**：
  - 入口承担明确的失败清理职责，且现有释放契约未覆盖时，在部分初始化或阶段失败后释放其负责的资源，再用 `throw;` 原样传播；不能仅因拥有资源就推导出必须关闭整个流程。
  - 明确可恢复的已知失败，且恢复业务已经定义（重试、返回上一界面、提示玩家）。恢复代码与判断依据写在 catch 内。
  - 已明确要求的流程失败退出：在操作入口或最外层更新边界捕获，停止并清理失败操作、调度返回入口，原异常继续上报。正常取消不进入失败退出，迟到异常不能退出新的操作；不为此监听全局异常或在每个辅助方法重复捕获。
  - 底层异常需要补充业务上下文时转换为具体异常，并保留 `InnerException`。只有确实补充了信息才转换，不做纯包装。
- **不允许的情况**：
  - 在每个辅助方法外包一层 try，理由是“多一层更安全”。
  - 用 catch 吞掉异常后只打印日志、返回默认值或继续流程。
  - 在 catch 中重复记录已由 `Forget()` 或上层统一上报的异常。
  - 用 try 代替空值检查、参数校验或状态判断。
  - 仅为“防止报错”在每帧的 `OnUpdate` 等热路径中包裹 try，掩盖内部错误。已有明确失败退出需求时，可以在最外层更新入口捕获、清理并调度退出，再原样抛出；不在内部每层更新重复捕获。
  - 只为重新抛出而捕获，没有任何清理或恢复动作。
- **捕获写法**：
  - 只捕获需要处理的类型。需要按条件区分时使用 `when` 过滤，不用 `catch (Exception)` 代替精确判断。
  - 重新抛出用 `throw;`，不用 `throw ex;`，以保留原始堆栈。
- **清理前确认归属**：异步任务可能在生命周期结束后才返回。清理前必须用 `IsCurrent` 或等价的身份检查确认它仍属于本次生命周期，不能关闭或释放已经属于新生命周期的资源。
- **清理动作保持幂等**：取消路径和异常路径都可能触发清理，Dispose 等入口允许重复调用，例如先置空引用再释放。
- **finally 与 catch 的选择**：清理必须在成功、取消、失败时都执行，且不依赖归属判断时用 `finally`。只在失败时清理，或需要先判断归属时，用 `catch` 后接 `throw;`。
- **取消异常默认直接传播**：`OperationCanceledException` 由所属生命周期发起（如整场 token）时，清理已由释放入口完成，异步入口不为取消单独写 catch。UniTask 的 `Forget()` 默认不上报取消异常。只有取消需要额外的本地动作时才单独捕获，并用 `when (token.IsCancellationRequested)` 限定。
- **确需失败清理时，不重复设置同一职责的捕获边界**：在能负责处理的入口清理，内部辅助方法不重复 try；没有明确失败清理需求时，不为建立“入口边界”而增加捕获。`Forget()` 或 `UniTaskVoid` 中未捕获的异常由 UniTask 统一上报，业务不得吞掉或重复记录。
- **框架内部任务不假定可被业务捕获**：TE 内部独立启动的 UI 加载等任务，其异常不一定回到 Procedure。业务不为此包装恢复机制，只在架构文档中说明边界。
- **需要立即释放的同步资源用 `using`**：IDisposable 资源优先用 `using`，不手写 try/finally。

新增或修改 try/catch 时，应能说明捕获的类型、捕获原因、清理或恢复动作、重新抛出方式，以及异常由哪一层统一上报。

## 5. 编码前思考

开始实现前必须完成以下判断：

1. 需求是否清楚且可验证。
2. 是否存在多种会显著影响结果的合理理解。
3. 是否有更简单的现有实现或项目能力可以复用。
4. 方案是否引入新的技术债、依赖或维护成本。
5. 实现是否超出当前任务和阶段边界。

如果关键需求存在歧义，应给出互斥选项并请求用户选择，不得默默替用户做高影响决策。

如果用户方案会明显增加技术债、违反项目硬约束或存在更简单可靠的方案，应先说明结论、原因和替代方案。

## 6. 极简优先

实现前和交付前分别进行一次极简检查：

- 是否加入了需求未指定的扩展点、配置项或兼容层。
- 是否为尚未出现的场景增加了抽象。
- 是否可以删除一层包装而不损失语义。
- 是否可以复用已有对象而不是创建平行体系。
- 是否用 50 行能够清楚完成，却写成了 200 行。

如果答案表明实现绕得没有必要，应缩减到满足当前验收标准的最小方案。

## 7. 目标驱动执行

### 7.1 将指令转为验收目标

多步任务开始时，将需求转换为可验证目标：

```text
目标
-> 实现步骤
-> 每步验证方式
-> 最终验收条件
```

例如修复缺陷时，优先建立可复现测试，再修复实现并让测试通过；新增功能时，先确认行为边界和验收用例，再实现最小闭环。

玩法功能任务不能只列类型名、模块名或架构目标。进入开发前，任务说明必须先回答“游戏里具体会发生什么”，再映射到代码。默认按以下顺序描述：

1. **玩法目的与可观察行为**：玩家能做什么，战场状态会如何变化。
2. **具体场景与数值示例**：使用一组明确输入演示完整成功流程。
3. **成功、失败与边界规则**：分别说明允许条件、拒绝条件及失败后的状态。
4. **状态变化与时序流程**：明确校验、资源提交、效果结算和回合推进的先后顺序。
5. **开发任务与职责归属**：将玩法规则映射到需要修改的 Data、Runtime、Resolver、Session、Presentation 等对象。
6. **验收测试**：以可观察结果覆盖成功、失败、边界和无副作用要求。
7. **非目标**：明确当前任务暂不实现的系统，防止范围膨胀。

如果任务说明只有“新增某类”“接入某系统”等工程词汇，开发者仍无法据此还原玩法，则需求尚未达到可开发状态。此时应先补充玩法规则和示例，不得要求开发者仅凭类名猜测策划意图。

### 7.1.1 会改状态的玩法动作：逻辑事务检查清单

凡任务会改多个战斗状态（如 AP、耐久、位置、回合当前单位、行动日志），描述时除 7.1 七段结构外，再套用下列心智模型。目标是强化“边界意识”，不是引入数据库事务框架。

```text
1. 改哪些状态？
2. 进入修改前，要证明哪些条件？
3. 中途失败时，哪些改动绝不能留下？
4. 结束后，如何让测试 / UI / 回放看懂发生了什么？
```

对应到任务描述时，优先落到这四段：

| 段 | 问题 | 写进任务的哪里 |
| --- | --- | --- |
| 契约检查 | 调用参数是否合法 | 成功/失败规则中的“调用错误” |
| 玩法检查 | 规则是否允许，且必须只读 | 成功/失败规则与无副作用要求 |
| 状态提交 | 通过后按固定顺序改世界 | 状态变化与时序流程 |
| 结果记录 | 成功失败都可观察 | 验收测试与 Result/Log/Snapshot |

默认提交顺序原则：

```text
先完成全部只读校验
-> 再提交资源消耗
-> 再结算效果
-> 最后记录结果
```

失败分两类，任务里要分开写：

- **调用契约错误**：空引用、未注册对象等，可抛异常，不进入玩法失败日志。
- **玩法拒绝**：资源不足、同阵营、越距等，返回失败结果并记日志，但权威状态不变。

验收时至少证明：

1. 成功路径状态与日志一致。
2. 玩法失败路径无副作用。
3. 不存在“只改了一半”的可观察中间态。

本清单用于描述和审查任务；概念展开见个人知识库《规则表达与战斗公式 / 07_事务与原子性》，不在本文重复长文。


### 7.2 持续执行

- 多步任务先建立计划，每一步都绑定验证点。
- 完成修改后运行项目规定的测试、类型检查、编译或静态检查。
- 验证失败时继续定位和修复，不以“代码已写完”作为完成标准。
- 只有全部验收通过，或存在必须由用户处理的明确阻塞时，才结束任务。
- 阻塞报告必须包含结论、原因、已完成内容和下一步解除方式。

## 8. 沟通规范

所有分析、方案、汇报、Issue 和 PR 描述遵循金字塔原理：

1. 先给结论或目的。
2. 再给背景和关键依据。
3. 然后说明方案或改动点。
4. 最后说明影响、风险和验证结果。

结构化内容应尽量按互斥且穷尽的方式分组，避免同一信息在多个章节重复。

用户提供的内容结构混乱时，应先按上述顺序重组，再输出或写入文档。

## 9. Git 工作流

- `main` 是稳定分支，功能和修复从 `main` 创建独立分支并通过 PR 合并。
- 禁止直接向 `main` 提交功能改动，禁止向 `main` 强制推送。
- Commit 遵循 Conventional Commits，例如 `feat:`、`fix:`、`refactor:`、`docs:`、`test:`、`chore:`。
- 保持原子提交，一个 Commit 只解决一个关注点。
- 提交前检查完整暂存差异、文件清单和敏感信息，并运行对应验证。

若当前项目已有更具体的 Git 决策或用户给出明确提交安排，以对应决策和当前指令为准。

## 10. 交付前检查

交付前确认：

- [ ] 实现满足当前任务的验收标准。
- [ ] 没有引入需求之外的功能。
- [ ] 没有重复已有能力或引入不必要依赖。
- [ ] 函数、类和文件职责清楚，规模合理。
- [ ] 错误和外部输入得到显式处理。
- [ ] 防御对应真实风险，没有重复校验内部不变量或静默掩盖编程错误，也没有删除必要的边界保护。
- [ ] 新增或修改的 try/catch 能说明捕获类型、捕获原因、清理或恢复动作、重新抛出方式和统一上报层。
- [ ] 没有硬编码或输出敏感信息。
- [ ] 差异只包含必要修改。
- [ ] 测试、编译和静态检查已通过。
- [ ] 若任务会改多个状态，已用逻辑事务清单核对检查/提交/失败无副作用。
- [ ] 汇报先结论后依据，并说明验证结果和剩余风险。
